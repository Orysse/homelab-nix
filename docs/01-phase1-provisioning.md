# Phase 1 — Provisioning the host and the microVMs

> Historical plan: phase 1 was completed on 2026-10-07 (gates G0–G6). The layout below is
> the original target; the current layout is described in the README.

## Goal

A NUC10 (16 GB RAM) running NixOS that, after **any reboot**, starts 3 microVMs on its own,
reachable over SSH on the LAN, entirely derived from the flake. No k3s in this phase.

Out of scope: k3s, Longhorn, sops-nix, Datadog, cert-manager, ingress, NAS backup.

## Step 0 — Ask the owner

Do not start writing code before having these answers. Record them in `docs/facts.md`.

1. **Where does Claude Code run?** On a laptop (architecture and OS? a Mac/ARM cannot build `x86_64-linux` without a remote builder) or directly on the NUC?
2. **NUC hardware**: exact model, RAM (16 GB?), disks (NVMe only? an extra SATA?) with their `/dev/disk/by-id/…` paths, virtualization (VT-x) enabled in the BIOS, UEFI boot.
3. **Can the disk be fully wiped?** Does it contain anything to keep? (Explicit answer required before any installation.)
4. **Network**: is the NUC on wired Ethernet? Interface name? Subnet, gateway, DNS. Which range of static IPs outside DHCP for the host (+ future hosts) and the VMs (3 now, with headroom)?
5. **Identity**: host name (proposed default: `nuc1`), node names (default: `kube-1..3`), timezone (`Europe/Paris`?), keyboard layout/locale, **public** SSH key(s) to authorize.
6. **nixpkgs channel**: `nixos-unstable` by default (like the reference repository) unless preferred otherwise. `flake.lock` is versioned.
7. **Where is the repository hosted** (private? public?). Reminder: never any secret in it.

Emergency access: have a screen and keyboard that can be plugged into the NUC during the first
tests (a bridge mistake on a headless machine = unreachable machine).

## Step 1 — Flake skeleton

Expected inputs: `nixpkgs`, `flake-parts`, `import-tree`, `disko`, `microvm` (`preservation` removed, see D1)
(all with `inputs.nixpkgs.follows = "nixpkgs"` where possible).

Target layout (to adapt, the logic matters more than the names):

```
flake.nix                      # minimal: inputs + import-tree ./modules
hardware/nuc1.nix              # generated by nixos-generate-config, OUTSIDE modules/
modules/
├─ parts.nix                   # systems = [ "x86_64-linux" ]; imports flakeModules.modules
├─ cluster/
│  ├─ options.nix              # declares options.cluster.{network,hosts,nodes}
│  ├─ topology.nix             # THE DATA (single source of truth)
│  └─ assertions.nix           # evaluation-time checks
├─ system/
│  ├─ base.nix                 # nix settings, timezone, base packages
│  ├─ users-ssh.nix            # public keys, sshd, passwordless root
│  ├─ boot.nix                 # systemd-boot, systemd initrd
│  ├─ disk-layout.nix          # disko: ESP + btrfs with subvolumes
│  └─ network-bridge.nix       # br0 + attachment of the vm-* taps
├─ virtualization/
│  ├─ microvm-host.nix         # microvm.nix host module; generates microvm.vms from cluster.nodes
│  └─ microvm-guest.nix        # common guest base
└─ hosts/
   ├─ nuc1.nix                 # disko (device), hardware, host IP, composition + nixosConfigurations.nuc1
   └─ nuc2.nix                 # PLACEHOLDER, evaluation only, never deployed (see gate G5)
docs/
```

## Step 2 — Data model and assertions

Implement `options.cluster` and `topology.nix` following `docs/00-architecture.md` §3, with the
assertions: unique names of ≤ 12 characters, unique IPs inside the subnet, existing `host`,
unique derived MAC. Write a small negative test (e.g. two nodes with the same IP must make
evaluation fail).

## Step 3 — Host

- **Disk (disko)**: GPT, 1 GB ESP + one btrfs partition (`-L nixos`) with subvolumes `@root` → `/`, `@nix` → `/nix`, `@log` → `/var/log`, `@microvms` → `/var/lib/microvms` (`compress=zstd,noatime`). A single pool rather than fixed partitions: no size to guess. Swap: zram only.
- **No impermanence** (D1 revised).
- **Boot**: systemd-boot + EFI. **No LUKS** in phase 1 (D2).
- **Access**: passwordless root, key-only SSH. **No plaintext password, no placeholder key** in the repository.
- **Network**: systemd-networkd; `br0` bridge; the physical Ethernet is enslaved to `br0`; the host's static IP is on `br0`; the `vm-*` taps are attached to `br0`. Follow the official example (✅: `matchConfig.Name = [ "<nic>" "vm-*" ]` → `Bridge = "br0"`). Firewall: do not blindly trust `br0` — open what is needed (SSH).
- Do **not** set the NIC name "from memory": read it from `facts.md`.

## Step 4 — microVMs

- Host: import `inputs.microvm.nixosModules.host`. **qemu** hypervisor (virtiofs support, most compatible).
- Generate `microvm.vms.<name>` for each `node` whose `host == <this host>`. "`config`" style (fully declarative, in the host closure): ✅ the documented form; the documentation warns that it increases build time and host closure size (acceptable here).
- Each guest (`microvm-guest.nix`):
  - hostname = node name; the node's static IP; gateway/DNS from `cluster.network`.
  - interface: `type = "tap"`, `id = "vm-<name>"`, derived `mac`.
  - ✅ Guest network: `systemd.network.networks."20-lan".matchConfig.MACAddress = <derived mac>` with `DHCP = "no"` (D13: not `Type = "ether"`).
  - `/nix/store` share: `{ source = "/nix/store"; mountPoint = "/nix/.ro-store"; tag = "ro-store"; proto = "virtiofs"; }`.
  - **no `microvm.volumes`**, **no** `writableStoreOverlay`. The root stays the default tmpfs.
  - sshd enabled, public keys authorized (reuse the host's building block).
  - RAM/CPU from the topology (2 GB / 2 vCPU each in phase 1, see the budget below).
- **Stable identity** (see D4): one virtiofs share per VM, `source = /var/lib/microvms/<name>/persist` on the host, mounted at `/persist` in the guest; `services.openssh.hostKeys` points into it. ✅ `machine-id`: already deterministic via `microvm.machineId` (default derived from the hostname).
- ✅ `autostart` defaults to `true` (set explicitly anyway); `restartIfChanged` defaults to `true` in `config` style.
- ✅ RAM: **never exactly 2048 MB**, QEMU hangs (microvm.nix#171 warning) → 2000 MB.

### Memory budget (16 GB)

| Item | GB |
|---|---|
| NixOS host (+ page cache) | ~2 |
| 3 VMs × 2 GB (phase 1) | 6 |
| headroom | ~8 |

In phase 2, k3s + Longhorn + the Datadog agent will push each VM towards 3–4 GB: 3 × 4 = 12 GB +
2 GB host = **tight**. Keep node RAM in the topology so it can be adjusted without touching
anything else. A qemu VM's RAM is reserved, not shared dynamically.

## Step 5 — Installing on the NUC (the owner does the physical part)

**Human actions**:
1. In the BIOS: UEFI, VT-x enabled, Ethernet plugged in.
2. Flash the minimal NixOS ISO to a USB stick and boot the NUC from it.
3. Make `ssh root@<NUC-ip>` work from Claude Code's machine (typically: put the public key in `/root/.ssh/authorized_keys` from the installer console). Note the IP.

**Claude Code actions** (after explicit confirmation that the disk may be wiped):
- Install with `nixos-anywhere` (`nix run github:nix-community/nixos-anywhere -- --flake .#nuc1 --target-host root@<ip>`), which runs disko then installs. Generate the hardware configuration with nixos-anywhere's generation option (`--generate-hardware-config nixos-generate-config ./hardware/nuc1.nix`) — check the exact flags with `--help`.
- If the build must happen on the NUC (non-x86_64 laptop): `--build-on remote`.

## Validation gates

Each gate must be **demonstrated** (command output pasted into the report), not assumed.

| Gate | Test | Expected |
|---|---|---|
| **G0** | `nix flake check`; build of the `nuc1` toplevel; evaluation of `nuc2`; negative test (duplicate IP) | everything passes except the negative test, which fails as intended |
| **G1** | on the host: `findmnt -R /`; reboot | subvolumes mounted as expected; key SSH OK, password refused |
| **G2** | on the host: `systemctl list-units 'microvm@*'`; from the laptop: `ssh` to each IP; in a VM: `findmnt /`; `find /var/lib/microvms -name '*.img'` | 3 VMs active and reachable; `/` = tmpfs; **no `.img` image** |
| **G3** | `ping` between the 3 VMs; `ping` VM → LAN/Internet | OK |
| **G4** | `reboot` the host, without any intervention | the 3 VMs come back on their own; note the delay; **each VM's SSH fingerprint unchanged** |
| **G5a** | `systemctl restart microvm@kube-2` | only kube-2 restarts; same IP, same SSH fingerprint, same machine-id |
| **G5b** | (evaluation only) set `kube-3.host = "nuc2"` in the topology | `nix eval` shows kube-3 absent from `nuc1` and present in `nuc2`; no other file changed |
| **G6** | change a VM's configuration (e.g. a package), `nixos-rebuild switch`, observe | the VM uses the new closure (see D5) |
| G7 (demo bonus) | `nixos-rebuild switch --rollback` | back to the previous generation, VMs included |

## Known pitfalls of the initial draft (untested, NOT to be reused as is)

1. btrfs reset at boot via `boot.initrd.postDeviceCommands` → no longer relevant (no impermanence on the host).
2. `inputs.microvm.flakeModule` imported in `parts.nix` → not confirmed that this export exists; do not assume it.
3. Forgetting `inputs.flake-parts.flakeModules.modules` → without it, `flake.modules.nixos.*` defined in several files does not merge.
4. Guest interface assumed to be `eth0` → wrong/not guaranteed; match the derived MAC (D13).
5. `hardware-configuration.nix` in `modules/` → import-tree would treat it as a flake-parts module and break evaluation.
6. "persistent" and "rw-store" `.img` volumes per VM → contrary to the core principle; removed.
7. Hard-coded values (`10.0.10.x` IPs, `eth0`, `/dev/sda`, placeholder SSH key, root password) → everything comes from `facts.md` / the topology.
8. Plaintext k3s token → to be handled in phase 2 with sops-nix.
